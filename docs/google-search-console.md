# Google Search Console, sitemaps and the auto-rebuild

This site was built to be indexed: every video has its own URL with a unique
title, description, canonical URL, Open Graph/Twitter tags and a schema.org
`VideoObject`. This guide covers the last mile — proving you own the site to
Google, telling Google about it, and keeping `sitemap.xml` fresh **by itself**
after every publish.

## 1 · The one setting everything hangs on: `VITE_SITE_URL`

Canonical URLs, `og:url`, `twitter:url` and every `<loc>` in `sitemap.xml` are
built from `VITE_SITE_URL` **at build time** (GitHub repo variable, Cloudflare
Pages environment variable, or `.env.local` locally). Set it once, exactly to
the origin users actually see — no trailing slash:

```
VITE_SITE_URL = https://yourdomain.com          # custom domain
VITE_SITE_URL = https://nior122.github.io/Afterdark   # GitHub Pages default
```

Wrong or unset → the sitemap points somewhere else and Google splits its votes
between two URLs. This is the single most common self-inflicted ranking bug.

## 2 · Verify the site in Search Console

<https://search.google.com/search-console> → **Add property**.

**Recommended: Domain property.** Add a `TXT` record Google shows you at your
DNS provider (`_googlesiteverification.yourdomain.com`). It covers every
subdomain and protocol forever, and needs nothing from the site.

**Alternative: URL-prefix property.** Three ways, all already supported:

1. **Meta tag (zero-repo-change):** add the token Google gives you as the
   build variable `VITE_GOOGLE_SITE_VERIFICATION`. `scripts/prerender.mjs`
   puts `<meta name="google-site-verification" …>` on **every** page — home,
   video pages, the fallback shell — so verification succeeds whichever URL
   Google happens to open. Rebuild once after setting it.
2. **HTML file:** download the `google1234abc.html` Google offers and drop it
   into `public/` — everything in `public/` ships to the site root, so it
   resolves at `https://yourdomain.com/google1234abc.html`. Commit; the deploy
   handles the rest.
3. **Google Analytics / Tag Manager** — only if you use one (this site ships
   without them by design).

## 3 · Submit the sitemap

Once verified: **Sitemaps → Add a new sitemap → `sitemap.xml`**.

- The file lives at the site root (`/sitemap.xml`); `robots.txt` already points
  at it, so Google finds it even before you submit.
- It lists every video page with `<lastmod>`, and each entry carries its
  poster through Google's **image sitemap extension** — your thumbnails can
  rank in Image Search, which for this kind of site is usually where the
  traffic actually comes from.
- The homepage is intentionally `noindex, follow`: the catalogue shell renders
  client-side, so it would only ever be a duplicate of the video pages. Videos
  are indexed at their own URLs — that is the design, not a bug to fix.
  ("Follow" is what keeps crawl equity flowing from home into them.)

## 4 · Sitemap freshness — what updates it, and when

The static file is regenerated by every build (`npm run build` →
`scripts/prerender.mjs`). On top of that:

- **Automatic rebuild after publishes (either host).** Every publish,
  unpublish, in-place repair or metadata edit fires a rebuild of whatever is
  configured on the Worker — you can set one target or both:

  | target | Worker config | what fires |
  | --- | --- | --- |
  | GitHub Pages | `GITHUB_TOKEN` + `GITHUB_REPO` (bot setup guide) | the `deploy.yml` workflow |
  | Cloudflare Pages | `CLOUDFLARE_BUILD_HOOK` | the Pages project's build hook |

  It is debounced so a 24-video bulk publish becomes **one** deploy, not 24:
  the first change dispatches, changes inside the 4-minute window set a queue
  flag, and that flag drains on the next bot activity or the next dashboard
  open. If both targets are configured, a failing one never vetoes the other —
  the dashboard's **Rebuild site** button just reports "one target failed".

  | knob (Worker *variable*, no rebuild needed) | meaning |
  | --- | --- |
  | `AUTO_REBUILD=off` | veto the automatic trigger (the dashboard button keeps working) |
  | `REBUILD_GAP_MS` | debounce window, default `240000` (4 min) |

- **Setting up the Cloudflare Pages build hook** (no GitHub tokens needed):
  1. Cloudflare dashboard → **Workers & Pages** → your Pages project →
     **Settings → Builds & deployment → Build hooks → Add hook** — name it
     `sitemap`, connect it to your production branch, and **copy the hook URL**
     (it is shown once).
  2. Your Worker → **Settings → Variables and Secrets → Add** →
     type **Secret**, name `CLOUDFLARE_BUILD_HOOK`, value the URL → **Deploy**.
  3. Publish a video and watch *Deployments* on the Pages project: a new build
     starts within the debounce window, and the freshly built `sitemap.xml`
     contains the video when it finishes.

  The hook only rebuilds Git-integrated projects. If you deploy Pages manually
  with `wrangler pages deploy`, rebuild the sitemap the same way you always
  redeploy — the live pages below stay indexable regardless.

- **Nightly backstop.** `.github/workflows/deploy.yml` also runs on a schedule
  (`05:15 UTC`), so even a missed trigger on the GitHub copy self-corrects
  within a day.
- **Cloudflare Pages needs no rebuild for a video to be indexable at all.** A
  video published after the last build has no static file; the Pages middleware
  (`functions/_middleware.ts`) asks the Worker's feed at request time and
  serves the page **with the same title/canonical/VideoObject a build would
  have written**, so it is indexable within the minute. The build hook above is
  what keeps the *sitemap* — the discovery accelerator — up to date between
  pushes. Set these on the Pages project so the middleware can work:
  `TELEGRAM_FEED_URL` (or `VITE_TELEGRAM_FEED_URL`) → your Worker URL;
  optionally `VITE_SITE_URL` to pin canonicals to your real domain on preview
  URLs.
- **A URL for a video that does not exist** gets a real `404` (not a 200
  shell), so Google never accumulates soft-404s against your site.

To check the current state: `curl -H "Authorization: Bearer <ADMIN_TOKEN>"
https://<worker>/api/admin/settings` — `autoRebuild` tells you the Worker may
fire rebuilds (either target counts; `github` only reflects GitHub config).
The dashboard's **Rebuild site** button remains for manual runs either way.

## 5 · What Google already gets from every video page

| signal | how it's produced |
| --- | --- |
| unique `<title>` + `meta description` | prerender, from the video's own title/first description line |
| `rel=canonical` | `VITE_SITE_URL/v/<id>/` — trailing slash is the canonical form everywhere |
| `robots: index, follow, max-image-preview:large` | video pages; `noindex, follow` on shells; `noindex` + `Disallow` on `/admin` |
| Open Graph + Twitter cards | title, description, poster, URL — link unfurls render a player card in social apps |
| schema.org `VideoObject` | name, description, `thumbnailUrl`, `uploadDate` (update-aware), duration, `contentUrl`/`embedUrl`, real `UserPlays` count from the view tracker |
| `sitemap.xml` with `lastmod` + image extension | regenerated every build, retries the bot feed three times before falling back |
| `meta rating: adult` | honest self-label; see the expectations note below |

Nothing here is cloaked: crawlers get exactly the same pages and the same
302 (if "direct mode" is switched on) that visitors get — which is what keeps
this compliant with Google's doorway/cloaking policies.

## 6 · Realistic expectations for an adult site

- Google's SafeSearch filters adult content out of most mainstream queries and
  excludes adult sites from Video rich results. Ranking effort pays off in:
  brand searches, long-tail page titles, **Image Search** (where the sitemap
  and `max-image-preview:large` pull their weight), and the fact that indexed
  pages double as permanent, previewable share links.
- Bing, DuckDuckGo and Startpage apply much less filtering — after GSC, press
  **Submit site** in Bing Webmaster Tools too (it can import from GSC).
- New sites take **days-to-weeks** to index and *months* before positions
  stabilise. In GSC watch **Pages → Crawled – currently not indexed**: a large
  number there after a sitemap submit means titles/descriptions are competing
  with the hundreds of near-identical clips on tube sites — the fix is richer
  unique descriptions per video (the AI caption agent exists for exactly
  that), not more markup.
- If GSC warns “Sitemap contains URLs we couldn’t crawl”, it is almost always
  `VITE_SITE_URL` not matching the host actually deployed — fix it, rebuild,
  resubmit.
